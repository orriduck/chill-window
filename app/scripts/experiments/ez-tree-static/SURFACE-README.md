# Fixed tree surface impostors

This separate cloud recipe prepares Ash Large (seed 29919) and Oak Large (seed 23399) from EZ-Tree commit `dcf309bd86bd521083d9c70f01f2de45fdc7c457`. It decodes the exact already-reviewed LOD0 raw positions, UVs, indices and split normals. It never rerandomizes the trees, modifies source PNG/JPG bytes or imports/reconverts GLBs. The original studio frames, filenames and manifests remain separate and intact.

The camera retains the eight horizontal 45-degree views, 512×512 resolution, 48 Eevee samples, 22m orthographic frame, 80m distance and target height 10.5m. Frame bounds are `[-11,-0.5,11,21.5]`; the root projects to `(256,500.3636)`. The uniform 20m source-height scale is a presentation choice. These author presets and normals are appearance proxies, not measured local trees or surveyed Hudson species/locations.

Albedo uses the existing sRGB leaf/Bark001 color images, decoded to linear and multiplied by the exact GLB `baseColorFactor`. As in `make-glb.py`, the normalized source HEX components are treated as **linear factors**, with no additional sRGB conversion of the factor. Emission strength is one, without studio lights or RGB gains. Standard view transform and zero exposure produce sRGB color PNGs.

Normal frames use `ShaderNodeNewGeometry.Normal` for leaf split shading normals and the original Bark001 NormalGL texture through a tangent-space `ShaderNodeNormalMap` on UVMap for branches. Both node outputs are interpreted in Blender world space. Before baking, eighteen actual cloud renders of known axis planes test Geometry, flat NormalMap and non-flat NormalMap outputs from the front and back; two additional off-center grazing renders test projection-aware face-forward behavior. The canonical object-local +Z plane is rotated with an object transform into each known world axis, so the probes distinguish world-space output from object-local output. The non-flat map encodes tangent normal `(0.3,0.4,sqrt(0.75))`; the converted UV plane has `T=+X, B=-Y, N=+Z`, so its expected front shading normal is analytically `(0.3,-0.4,sqrt(0.75))` before object rotation and world-to-tree conversion. This detects bitangent/green-channel sign mistakes that a flat map cannot reveal. The explicit face-forward operation uses `dot(normal, Geometry.Incoming)`, negating normals pointing away from the actual view direction; leaf surfaces are double-sided, while branch backfaces are culled as in the GLB. Blender world `(X,Y,Z)` is mapped to the unrotated Three tree's local `(X,Z,-Y)`, then encoded as `(N+1)/2` under the Raw view transform. These PNGs must be sampled as linear data / Non-Color.

The source GLB writes raw UV values unchanged. This bake maps them to Blender as `(U,1-V)` without changing source geometry or image bytes. This follows the [glTF upper-left texture-origin convention](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/Specification.adoc#textures) and Blender 4.0.2's [official UV conversion](https://github.com/blender/blender-addons/blob/v4.0.2/io_scene_gltf2/blender/imp/gltf2_blender_mesh.py#L525-L528). The official [normal material path](https://github.com/blender/blender-addons/blob/v4.0.2/io_scene_gltf2/blender/imp/gltf2_blender_pbrMetallicRoughness.py#L467-L500) passes original RGB directly to NormalMap, while the [texture helper](https://github.com/blender/blender-addons/blob/v4.0.2/io_scene_gltf2/blender/imp/gltf2_blender_texture.py#L62-L70) marks normal textures as data. Accordingly, no extra green-channel inversion is applied. Blender's [4.0.2 shader implementation](https://github.com/blender/blender/blob/v4.0.2/source/blender/gpu/shaders/material/gpu_shader_material_normal_map.glsl#L4-L24) supplies the tangent/bitangent/front-facing behavior tested by the probes. Sources checked on 2026-10-10. The manifest records these references and conversion provenance; the verifier independently reconstructs and compares the actual assigned Blender loop-UV byte hashes. Surface alpha footprints may differ from old studio frames, whose UV interpretation remains unchanged.

Geometry Incoming is world-space toward-camera: the [Geometry shader](https://github.com/blender/blender/blob/v4.0.2/source/blender/gpu/shaders/material/gpu_shader_material_geometry.glsl#L15-L19) uses `coordinate_incoming`, the [Eevee surface helper](https://github.com/blender/blender/blob/v4.0.2/source/blender/draw/engines/eevee/shaders/surface_lib.glsl#L231-L238) returns `cameraVec`, and the [view helper](https://github.com/blender/blender/blob/v4.0.2/source/blender/draw/intern/shaders/common_view_lib.glsl#L14-L19) selects constant inverse-forward for orthographic projection. Sources checked on 2026-10-10. A per-point `cameraPosition-worldPosition` vector is incorrect for these orthographic views. The regression probes place a nearly grazing plane at world `(0,5,10.5)` under the yaw-zero camera `(80,0,10.5)`, with normalized world normal `(0.02,0.9998,0)`. Its true view-direction dot is positive, while the perspective-position dot is negative. Both Geometry and flat NormalMap renders must retain the positive normal at its off-center projected pixel with opaque alpha, exposing the previous wrong sign.

Both passes use the exact same source alpha cutoff: discard interpolated leaf alpha below 0.5, including alpha exactly 0.5 as opaque. They use the same geometry/camera and transparent RGBA8 background. At 48 samples, antialiasing and overlapping leaf surfaces average different valid normals. Even an alpha-255 pixel can have a decoded length below one. Only the opaque calibration centers must have unit length within 1% quantization tolerance. Production checks require finite vectors of length at most 1.02 and report their real distributions, including opaque 3×3 interiors, edges, short vectors and near-zero vectors. Runtime should normalize the alpha-weighted decoded direction; short/zero vectors and visual behavior require inspection before integration. The verifier enforces exact paired alpha bytes. A mismatch writes actual counts, maximum byte delta and example pixels and fails; it never relaxes the contract automatically. Opaque albedo RGB statistics are observations, with no brightness target.

The workflow first rebuilds and verifies all original source content using the existing pinned scripts, installs Ubuntu's Blender `4.0.2+dfsg-1ubuntu8`, then calibrates, renders, verifies and packs. It uploads the 32 tree RGBA frames (16 albedo + 16 normals), calibration images/report, manifest, verification report, notices and four 2048×1024 runtime atlases. Every atlas cell is independently decoded and checked against its source RGBA pixel SHA-256 after saving. Channel color spaces, normal mapping, source hashes, seed bindings, actual bounds, cameras and Blender version are carried into the runtime manifest.

Run **in cloud only**, after recipe review:

```sh
bash app/scripts/experiments/ez-tree-static/rebuild-assets.sh
python3 app/scripts/experiments/ez-tree-static/verify-report.py
blender -b --python app/scripts/experiments/ez-tree-static/render_tree_surface_impostors.py -- \
  --source-root app/scripts/experiments/ez-tree-static \
  --out app/scripts/experiments/ez-tree-static/surface-impostors
/usr/bin/python3 app/scripts/experiments/ez-tree-static/verify-surface-impostors.py
/usr/bin/python3 app/scripts/experiments/ez-tree-static/pack-surface-impostors.py
```

`tree-surface-impostors.json`, `verified-surface-report.json` and `runtime/tree-surface-atlases.json` keep `runtimeImported` and `visualAcceptance` false. Successful calibration, pixel checks and packing establish preparation integrity; they do not establish actual scene appearance. Cloud output inspection and browser review in a Debug Mode capable of isolating surface channels and tree distances remain required before runtime acceptance. Keep the EZ-Tree MIT license and the upstream texture notice (including AmbientCG Bark001 CC0 links) with redistributed products.
